# PostgreSQL для состояния бота — дизайн

Статус: решение для реализации, 23.09.2026. Владелец задачи — Codex; пользователь подтвердил переход с SQLite на PostgreSQL. Этот документ относится только к хранению данных и серверному коду. UI, тексты диалога, нормативный справочник и действующий webhook MAX остаются за другими задачами.

## Исходное состояние и граница с командой

В `main` работает один процесс Node.js 24 с `node:sqlite`: `sessions` хранит JSON профиля, `events` защищает от повторной обработки webhook, `outbox` хранит ответы и напоминания. `Service.receive()` обновляет всё одной транзакцией. База находится в Docker volume `bot-data` на действующей ВМ; считать её пустой нельзя. Открытая PR #3 (`worktree-bot-calendar-buttons`) меняет `src/bot/store.ts`, `src/bot/service.ts`, `src/demo.ts`, `tests/bot.test.ts`, README и журнал решений. Эти файлы интегрируем только после слияния PR #3 или явной передачи их владельцем. Будущий UI не правит таблицы напрямую: его серверный контракт должен обсуждаться отдельно с разработчиком UI.

## Выбор

Рабочий процесс бота переходит на PostgreSQL; SQLite остаётся только источником одноразового переноса старых данных. Используем `pg` с параметризованными запросами и одним клиентом на транзакцию. Бот остаётся одним процессом в MVP, но выбор задания из очереди атомарный и допускает несколько работников. Нового пользовательского HTTP API нет.

Рассмотрены три варианта: укрепить SQLite (меньше изменений, но не выполняет запрос на PostgreSQL), держать оба хранилища как постоянные runtime-адаптеры (двойная поверхность ошибок), заменить runtime-хранилище на PostgreSQL с отдельным импортом (выбрано). База обязана переживать рестарт, повтор webhook, временный сбой MAX и смену версии нормативного справочника ровно как сейчас.

## Таблицы и инварианты

Миграция `001` создаёт `schema_migrations`, `sessions`, `events`, `outbox`. Идентификатор MAX — положительный `BIGINT`, проверяемый на безопасный целый тип при входе и при чтении. `sessions.data` и `outbox.payload` — `JSONB`; время в миллисекундах Unix (`BIGINT`), чтобы импорт сохранял точные значения. `events.id` и `outbox.id` — первичные ключи идемпотентности. `outbox.kind` принимает `reply` или `reminder`; `status` — `pending`, `sending`, `sent`, `cancelled`, `failed`. Для `sending` есть `lease_token` и `lease_until`. Частичные индексы обслуживают выбор готовых и просроченных заданий; отдельный индекс — удаление заданий пользователя.

Входящее обновление берёт транзакционную блокировку по `user_id`, вставляет ID события, читает профиль, вычисляет переход и записывает профиль, ответ и расписание. При любой ошибке откатывается и ID события. `maintain()` обрабатывает пользователей по одному, под той же блокировкой. Выбор задания — один `UPDATE … RETURNING` с `FOR UPDATE SKIP LOCKED`; подтверждение/повтор принимают только текущий `lease_token`. Просроченная аренда возвращает задание к обработке. После неопределённого ответа MAX дубль доставки возможен; гарантии прочтения нет.

`/delete` удаляет профиль и все его задания, но технический отпечаток входящего события живёт до семи суток, как описано пользователю. Неактивные профили удаляются после 400 суток. Завершённые и ошибочные задания удаляются по действующему правилу семи суток; pending не удаляются по возрасту.

## Перенос и развёртывание

Одноразовый импорт читает SQLite только на остановленном боте или из согласованного snapshot с WAL, проверяет типы и JSON, требует пустые таблицы PostgreSQL, переносит три таблицы одной транзакцией и сверяет количество строк. Он не печатает содержимое профилей и не удаляет исходную SQLite базу. До переключения сохраняются проверяемый backup PostgreSQL и исходный SQLite volume. Миграция схемы идемпотентна, фиксируется номером, не применяется частично.

В Compose добавляется PostgreSQL с отдельным volume и healthcheck. Имя пользователя/БД могут быть в конфиге, пароль только в `.env`, пример — плейсхолдер. Приложение не принимает webhook до успешной проверки соединения и миграции схемы. Проверки используют настоящий PostgreSQL в CI или локальном Compose; тесты с синтетическими профилями покрывают дедупликацию, откат, перенос, рестарт, очередь и удаление. После ревью переход на действующей ВМ выполняется отдельным коротким окном: остановка бота, snapshot, импорт, проверка, запуск, полный проход в мобильном и веб-MAX. Рабочую подписку и токен локальные тесты не трогают.

## Приёмка

`npm test`, `npm run typecheck`, `npm run build`, `npm run demo:check`, интеграционные тесты на PostgreSQL и `docker compose build` зелёные; сценарий переживает рестарт и сохраняет отметки. Проверены сверка числа импортированных записей, `/delete`, повтор webhook, отказ БД (HTTP 503), повтор доставки задания после ошибки. До реального прогона в MAX и проверки бэкапа нельзя писать, что переход на рабочем боте завершён.
