# Продуктовая рамка

Источник — «Дополнительная информация», стр. 16–20 в `Забота о людях.md`; веса — в
`CLAUDE.md`. Каждый артефакт — отдельный файл в `docs/product/`, он же потом слайд.
Утверждение без источника помечается как **допущение**, не как факт.

Порядок важен: проблема → As Is → To Be → гипотеза → MVP → масштабирование → пилот.
Технология выбирается после `problem.md`, не раньше.

## 1. `docs/product/problem.md`

```markdown
# Проблема

**[Пользователь]** в ситуации **[контекст]** хочет **[результат]**, но сталкивается
с **[барьером]**, из-за чего **[последствие]**.

## Пользователь
Жизненная ситуация / роль / территория / статус / этап пути. Почему именно этот
сегмент приоритетный.

## Проверка
| Вопрос | Ответ | Источник |
|---|---|---|
| Понятно ли, кто пользователь? | | |
| Какую конкретную задачу он решает? | | |
| Где в процессе возникает проблема? | | |
| Почему она значима (масштаб, частота, цена ошибки)? | | |
| Чем подтверждается существование? | | |

## Что уже есть
Что по этой ситуации есть на «Госуслугах», в МФЦ и у ведомств, и какой барьер
всё равно остаётся. Наше решение не дублирует существующий сервис.
```

Признаки хорошей проблемы (стр. 16): информация разбросана по источникам; неясно,
какая услуга или канал подходят; порядок зависит от территории или статуса; нужно
самому сопоставлять требования; путь через несколько организаций; ошибка на этапе
ведёт к возврату; важны следующий шаг, сроки и статус; ручной перенос данных между
сервисами; барьер языка, цифровых навыков или здоровья.

Анти-паттерн: «создадим AI-ассистента / навигатор / агрегатор» как стартовая формулировка.

## 2. `docs/product/as-is-to-be.md`

```markdown
# As Is
| Этап | Что делает пользователь | Сервисы/документы/специалисты | Нужные данные | Где теряется время | Где ошибки/неопределённость | Что вручную |
|---|---|---|---|---|---|---|

Точка воздействия: <одна наиболее значимая точка и почему>

# To Be (только выбранный участок)
| Было | Станет | Тип изменения (исчезает / упрощается / автоматически / быстрее) |
|---|---|---|

Зачем нужен продукт — одним предложением из сравнения.
```

## 3. `docs/product/hypothesis.md`

```markdown
Если мы поможем **[пользователю]** выполнить **[действие]** с помощью
**[механики продукта]**, **[результат]** станет **[лучше]**, потому что **[обоснование]**.

| Метрика | Сейчас (источник или допущение) | Цель | Как измерим на пилоте |
|---|---|---|---|
```

Метрики-кандидаты: время процесса, число ручных действий, число ошибок, доля
завершивших сценарий, число повторных обращений, точность подбора.

## 4. `docs/product/mvp.md`

```markdown
MVP — минимальная версия, в которой пользователь полностью получает основной результат.

## Основной сценарий
Шаги от входа в бота до результата. Что в чате, что в мини-приложении и почему
(чат: последовательные вопросы, статусы, напоминания; мини-приложение: сложные
формы, списки, сравнение, возврат к данным).

| MoSCoW | Функция | Почему здесь |
|---|---|---|
| Must Have | | без неё сценарий не работает |
| Should Have | | |
| Could Have | | только после готовности Must |
| **Won't Have** | | сознательно не делаем в этой версии |

## Данные
| Данные | Реальные / тестовые / [MOCKED] | Источник, дата, территория | Что нужно для реальной интеграции |
|---|---|---|---|
```

Блок Won't Have обязателен: условия прямо называют ограничение объёма частью
сильного решения.

## 5. `docs/product/scaling.md` — самый тяжёлый продуктовый критерий (35%)

```markdown
## Ядро (не меняется)
Проблема / логика сценария / архитектура / базовая модель данных / механика / ключевые элементы UI.

## Переменная часть (адаптируется)
| Что | Где живёт в нашем решении (файл/конфиг/справочник) | Что менять при переносе |
|---|---|---|
| Региональные данные | | |
| Нормативные требования | | |
| Перечень услуг и организаций | | |
| Справочники | | |
| Внешние ИС и интеграции | | |
| Роли участников | | |
| Правила и порядок предоставления | | |
| Язык и доступность | | |

## Вопросы
| Вопрос | Ответ |
|---|---|
| Где ещё существует аналогичная проблема? (конкретные регионы/организации/категории) | |
| Куда масштабируем в первую очередь и почему? | |
| Что переносится без изменений? | |
| Что адаптировать? | |
| Какие данные, интеграции, ресурсы понадобятся? | |
| Какие риски? | |
| Следующий шаг после успешного запуска? | |

## Порядок тиражирования
Этапы с условием перехода к следующему.
```

Проверка честности: колонка «Где живёт в нашем решении» заполнена ссылками на
реальный код или конфиг. Если переменная часть зашита в код, масштабирование — слова.

## 6. `docs/product/pilot.md` — нужен к финалу (сценарий запуска 15%)

```markdown
| Вопрос | Ответ |
|---|---|
| Для кого и где первый запуск (регион, организация, сегмент)? | |
| Как продукт встраивается в существующий процесс? | |
| Какие данные, интеграции, партнёры, владельцы процесса нужны? | |
| Как пользователи получат доступ (каналы привлечения)? | |
| По каким метрикам оценим результат (из hypothesis.md)? | |
| Какой следующий шаг после успешного пилота? | |
```

## Сверка с критериями

Перед презентацией пройти по подпунктам продуктовой оценки (стр. 12) и финала (стр. 14)
и для каждого указать файл из `docs/product/`, который его закрывает. Подпункт без
файла — пробел. Для независимой оценки запустить субагента `jury`.
