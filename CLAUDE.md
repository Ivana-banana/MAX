# CLAUDE.md — правила работы над проектом

Хакатон Минобрнауки России × MAX, трек **«Забота о людях»**: чат-бот или чат-бот
с мини-приложением в MAX, который решает конкретную задачу человека при работе с
государственными, муниципальными, социальными или медицинскими сервисами.

Условия — [`Забота о людях.md`](Забота%20о%20людях.md) (перенос PDF один к одному,
первоисточник — `Забота о людях.pdf`, его не редактируем). Справка по платформе —
`docs/max-platform.md`. Git — `GIT.md`, текущая работа — `HANDOFF.md`, решения —
`docs/decisions.md`, продуктовые артефакты — `docs/product/`.

Календарь: онлайн-этап (MVP + презентация, отбор в финал), дедлайн — **TBD, в PDF
не указан**; финал — очная защита **29 октября в Казани**. Неизвестные даты и
факты помечаем `TBD`, а не угадываем.

## Как здесь выигрывают

**Допуск.** Ноль баллов и дальше не оценивается, если: не по теме или MAX не
среда реализации; бот или мини-приложение не запускается или основной сценарий
нельзя пройти; нет презентации. Эти три пункта важнее всего остального.

Каждый критерий оценивается по шкале 0–3. Итог онлайн-этапа:

| Продуктовая оценка — 40% | | Техническая оценка — 60% | |
|---|---|---|---|
| Потенциал масштабирования | **35%** | Работоспособность и полнота основных функций | **30%** |
| Пользовательская ценность | 25% | Корректность интеграции и обмена данными | 20% |
| UX/UI и удобство взаимодействия | 20% | Техническая реализация и архитектура | 20% |
| Обоснованность и целостность | 15% | Стабильность и обработка ошибок | 10% |
| Качество презентации | 5% | Безопасность, зависимости, данные | 10% |
| | | Техдокументация и комплектность | 10% |

Плюс **+0,15** платформенного бонуса (только целиком): возможность MAX сверх
минимума, встроенная в основной сценарий и описанная в материалах. Собственный API
баллов не даёт. В финале: 40% техническая оценка + 60% защита; бонус не переносится.

Выводы, которые следуют из весов:

- Масштабирование — самый тяжёлый продуктовый критерий. Это не «запустим по всей
  России», а явное разделение на ядро и переменную часть (см. скилл
  `product-framing`). Архитектура с первого дня держит региональные данные,
  справочники и тексты вне кода.
- Основной сценарий, пройденный от начала до результата в настоящем MAX, стоит
  больше любого числа недоделанных функций.
- При дефиците времени порядок: (1) один сценарий работает end-to-end в MAX на
  мобильной и веб-версии; (2) README + Docker + `.env.example` по «Формату сдачи»;
  (3) презентация с продуктовой логикой; (4) обработка ошибок и состояния UI;
  (5) платформенный бонус; (6) полировка.

## Неподвижные ограничения (из условий)

- Бот или мини-приложение работает в MAX; основной сценарий проверяется в MAX и
  доступен **и в мобильной, и в веб-версии**. Мини-приложение подключается к боту и
  не живёт отдельным сервисом. Мини-приложение — только по HTTPS.
- **Ник бота генерирует платформа, выбрать или изменить его нельзя** (условия, п. 11;
  `docs/max-platform.md`). Название, логотип и описание менять можно, но это
  повторная модерация до 48 часов по рабочим дням — согласовать до подачи. Токен
  бота выдают организаторы.
- Никаких закрытых библиотек, частных API и кода без свободной лицензии.
- Токены, пароли, API-ключи и другие секреты в репозиторий не попадают никогда:
  только `.env` (в `.gitignore`) и `.env.example` с плейсхолдерами. Проверяет
  Stop-хук `check-secrets.sh`.
- Тестовые, заранее подготовленные или смоделированные данные вместо реальной
  интеграции **явно указываются** в README, презентации и в самом продукте.
- Российское законодательство и [правила платформы MAX](https://legal.max.ru/ps).
  Персональные данные — 152-ФЗ: реальные персональные и медицинские данные без
  законных оснований не используем.
- Сдача: работающее решение в MAX, зафиксированный commit, README по списку,
  lock-файл зависимостей, Dockerfile + compose + `.dockerignore` + `.env.example`,
  **сборка в Docker ≤ 5 минут** (без загрузки базовых образов), PDF-презентация
  с техническим первым слайдом. Полный чек-лист — скилл `submission-checklist`.
- После дедлайна код не меняется.

## Продукт: сначала проблема, потом технология

- Пользователь узкий: жизненная ситуация, роль, территория, статус, этап пути.
  «Граждане», «пациенты», «иностранцы» — недостаточно.
- Проблема формулируется по шаблону из условий и подтверждается источником.
  До выбора решения изучить, что уже есть на «Госуслугах», в МФЦ и на сайтах
  ведомств: решение не дублирует существующий сервис.
- Один приоритетный сценарий, реализованный до конца. Блок **Won't Have** в MoSCoW
  записывается явно — ограничение объёма часть решения, а не слабость.
- Не начинаем с «сделаем AI-ассистента / навигатор / агрегатор». LLM появляется
  только если закрывает подтверждённый барьер и это записано в `docs/decisions.md`.
- Бот или мини-приложение выбираются по условиям (стр. 15): последовательные
  вопросы, статусы, напоминания → чат; сложные формы, списки, сравнение → мини-приложение.
- Артефакты (проблема, As Is/To Be, гипотеза и метрика, MVP, масштабирование, пилот)
  лежат в `docs/product/` и напрямую переходят в слайды. Шаблоны — скилл
  `product-framing`.

## Данные, LLM и честность

- Разделяем в интерфейсе и в коде: **факт из официального источника**, **расчёт
  продукта**, **рекомендация**, **допущение / модельные данные**. Пользователь видит,
  откуда ответ, для какой территории и на какую дату.
- Любой сценарий на заглушке вместо реальной интеграции пишет в лог
  `[MOCKED: что и почему]` и помечен в UI. Список моделируемых интеграций и что нужно
  для реальных — в README. Не имитируем интеграцию так, чтобы её можно было принять
  за настоящую.
- Медицина: продукт не ставит диагноз, не интерпретирует симптомы и анализы, не
  назначает и не корректирует лечение. Юридически значимые процессы: ответ модели не
  выдаётся за решение ведомства.
- LLM на нормативке: ответ привязан к источнику, показано основание, есть ветка
  «надёжного ответа нет — вот куда обратиться». Предположение модели не выдаётся за
  официальный факт.
- Первоисточник важнее пересказа. У данных фиксируем дату обновления, территорию и
  период.

## Платформа MAX

- Документация MAX меняется: перед использованием метода сверяться с
  [dev.max.ru/docs](https://dev.max.ru/docs) и `docs/max-platform.md`. Старые примеры
  и сторонние статьи источником не считаются. Метод, которого нет в документации, не
  выдумывается; спорное помечается `TBD` со ссылкой.
- Версии SDK и библиотек (MAX Bridge, MAX UI и прочие) берём из lock-файла или реестра
  пакетов, а не из памяти.
- Кандидаты на платформенный бонус записываются в `docs/decisions.md` с объяснением,
  какую пользовательскую ценность они дают в основном сценарии.

## Код и архитектура

- Стек — **TBD** (организаторы советуют JavaScript и React). После выбора вписать
  сюда команды установки, запуска, тестов и линта.
- Плоский код: небольшие модули, явные типизированные контракты, никаких фабрик,
  реестров, DI-контейнеров и конфиг-движков «на будущее». Библиотеки — идиоматично и
  на полную; свои «платформы» поверх них — нет.
- Всё, что меняется при масштабировании (регион, справочники, перечень услуг,
  тексты, язык), живёт в данных или конфиге, а не в условиях кода. Архитектура
  допускает локализацию.
- Конфигурация — только через переменные окружения; дефолты без секретов.
- Каждое действие пользователя имеет состояния загрузки, результата и ошибки (прямой
  пункт критерия UX). Ошибка внешнего сервиса не превращается молча в успех и не
  роняет сценарий: пользователь может продолжить без перезапуска.
- Идентификаторы и комментарии в коде — английские; тексты для пользователя и
  документация — русские.
- Правки только в зоне задачи: не переформатировать и не рефакторить соседний код.

## Тесты и доказательство результата

- Новая логика → тест в том же коммите. Багфикс начинается с воспроизводящего теста.
- «Должно работать» не существует. Готово — это: тесты зелёные, основной сценарий
  пройден руками **в настоящем MAX** (мобильная и веб-версия), результат записан.
- `docker compose build` на чистом клоне с замером времени — перед каждой вехой и
  перед сдачей. Больше 5 минут — дефект.
- Stop-хук `check-tests.sh` сам находит `npm test` / `pytest` и не даёт закончить ход
  с красными тестами; пока тестов нет, он молчит. Сценарий в MAX хук не проверяет.
- Ни одно «проверено» / «работает» в чате, README или отчёте не пишется без команды и
  её вывода.

## Принципы Карпаты — адаптация под продуктовый хакатон

1. **Become one with the user.** До кода пройти путь пользователя руками на
   «Госуслугах» и сайтах ведомств, с источниками и скриншотами.
2. **Overfit a single scenario first.** Один сценарий от `/start` до результата в MAX,
   потом ширина.
3. **Тупой бейзлайн прежде умного.** Кнопки и готовые ответы раньше LLM; бот раньше
   мини-приложения. Усложнение должно улучшать метрику из гипотезы.
4. **Визуализировать всё.** Схема As Is/To Be, архитектура, скриншоты сценария — они
   же идут в презентацию.
5. **Воспроизводимость.** Одна команда запуска, зафиксированные версии, тестовые
   данные в репозитории.
6. **LLM fail silently.** Модель уверенно врёт — проверяем источником и тестом.
7. **Журнал решений.** Каждое продуктовое и техническое решение — строка в
   `docs/decisions.md`: что выбрали, почему, что отвергли. Это готовые ответы жюри.

## Работа с Claude Code

- Субагент `jury` (`.claude/agents/jury.md`) оценивает текущее состояние по критериям
  как проверяющий: видит только артефакты, не рассуждения автора. Запускать перед
  каждой вехой и перед сдачей.
- Скиллы: `submission-checklist` — проверка репозитория против «Формата сдачи»;
  `product-framing` — шаблоны продуктовых артефактов.
- Раз в несколько коммитов пересказать правила этого файла своими словами. Если
  правило пропущено, раздел пора сократить или вынести в скилл, а не выделять
  жирнее.

## Ревью

- Крупное или рискованное — ветка и ревью другим участником. Мелкое и безопасное — в
  `main` после зелёных проверок.
- Чек-лист: нет секретов; моки помечены; тест есть; основной сценарий не сломан;
  состояния ошибок есть; зависимости зафиксированы; решение записано.

## Git

Кратко (полностью — `GIT.md`): **задача, меняющая файлы, делается в своём worktree**
(`claude -w <поток>-<тема>` → `.claude/worktrees/…`, ветка `worktree-…`), а не в
основной копии на `main`; в `main` — только проверенный результат через
`git push origin HEAD:main` (fast-forward). Коммит и push **автоматически, без запроса
разрешения** после каждого законченного и проверенного шага; в коммит только свои
файлы через `git add <пути>`; перед работой и перед push —
`git fetch --prune && git status -sb`; историю `main` не переписываем, force-push
запрещён; трейлеры соавторства ИИ в коммиты не добавляем.
